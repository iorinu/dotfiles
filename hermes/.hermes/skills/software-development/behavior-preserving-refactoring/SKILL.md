# 振る舞いを保つリファクタリング

確定済み仕様と既存テストを守りながら、可読性、責務分離、重複、複雑さ、保守性を改善する。既定は局所的なリファクタリングだが、ユーザーが選択した場合は段階的な大規模リファクタリングも扱う。どちらの場合も、機能追加や仕様変更は行わない。

## When to Use

- 実装後に、読みやすさや保守性の観点でレビュー・改善したいとき
- 重複、複雑な条件分岐、責務の混在、分かりにくい命名を整理したいとき
- 機能要件への適合を保ったまま内部構造を改善したいとき
- モジュール分割、責務の再配置、依存方向の整理などを段階的に行いたいとき

使わない場面:
- 未修正の不具合や要件不適合があるとき。先に `spec-driven-delivery` を使う。
- 意図的に外部の振る舞い、公開 API、データ形式、性能特性を変更したいとき。

## 規模の選択

- **局所モード（既定）**: 変更対象とその周辺に限定する。SAFE と CAREFUL の変更をテストとともに適用する。
- **大規模モード（明示的に選択）**: モジュール分割、レイヤー再編、依存関係の逆転、重複した基盤の統合、段階的な API 移行を扱える。開始前に、対象範囲、維持する外部契約、移行方式、各段階の検証方法、ロールバック方法を提示し、ユーザーの承認を得る。

ユーザーが規模を指定していない場合、対象コードの広さ・公開契約・変更リスクを示して `clarify` で局所モードか大規模モードかを確認する。依頼が明確に局所的なら、局所モードを既定として進めてよい。

## 局所モードの手順

1. 変更境界と振る舞いの基準を確認する。
   - 現在の差分、仕様書、関連テスト、公開 API、呼び出し元を `read_file`、`search_files`、`terminal` で確認する。
   - 対象コードの既存テスト・lint・型検査・ビルドを実行し、リファクタリング前の基準結果を記録する。
   - 基準を取れない場合は、その理由とリスクを明示する。

2. 設計レビューを行う。
   - 命名、責務、重複、条件分岐、例外処理、データ変換、抽象化、コメントを `path:line` と根拠付きで確認する。
   - 影響が大きい提案は、期待する保守性の利益と破壊リスクを示す。

3. 提案をリスク別に扱う。
   - SAFE: 未使用 import、死んだ局所コード、重複コメントなど、外部振る舞いに影響しない改善は自動で適用できる。
   - CAREFUL: 局所的な抽出、内部名の変更、条件分岐の平坦化は、対象テストを実行しながら小さく適用できる。
   - RISKY: 公開 API、永続データ、並行性、エラー処理、性能特性、モジュール境界を変える改善は、事前にユーザーへ確認する。

4. 小さな単位でリファクタリングする。
   - 一回に一つの意図を変え、対象テストを実行してから次へ進む。
   - 機能を追加しない。仕様書を変更する必要が出たら止まり、ユーザーに確認する。
   - テストが不足していて安全性を確保できない場合、先に振る舞いを固定するテストを追加する。

5. 振る舞いを再検証する。
   - 手順 1 の品質検査を再実行し、基準結果との差分を確認する。
   - `spec-driven-delivery` の要件適合表を使い、仕様上の受入条件が引き続き満たされるか確認する。

## 大規模モードの手順

1. 現状と変更境界を調査する。
   - `read_file`、`search_files`、`terminal` で依存グラフ、公開 API、設定、永続データ、呼び出し元、統合テスト、デプロイや移行手順を確認する。
   - 影響を受ける契約を「維持」「段階移行」「廃止候補」に分類する。根拠のない分類はしない。

2. リファクタリング設計書を作り、承認を得る。
   - 目的、非目標、対象範囲、移行後の構造、段階、各段階で維持する契約、テスト戦略、ロールバック方法、リスクを記載する。
   - 互換性を壊す可能性、データ移行、設定形式・公開 API・外部副作用の変更がある場合は、実装前に `clarify` で承認を得る。

3. 移行前の安全網を作る。
   - 既存の振る舞いを固定する単体・統合・契約テストを追加し、失敗状態では次工程へ進まない。
   - プロジェクトで利用可能なテスト、lint、型検査、ビルドの基準結果を記録する。

4. 段階的に実装する。
   - 一段階ごとに互換層、アダプター、移行コードを必要最小限に置き、対象テストと品質検査を実行する。
   - 各段階で要件適合を確認し、失敗時は直前の安全な段階へ戻せる状態を保つ。
   - 互換層や旧実装の削除は、全利用箇所の移行と検証の根拠を確認してから行う。破壊的削除はユーザー承認を得る。

5. 移行を完了し、再検証する。
   - 旧・新経路、エラー処理、境界条件、性能上重要な経路、公開契約を確認する。
   - `spec-driven-delivery` の要件適合表を再実行し、仕様上の受入条件が維持されていることを示す。
   - 最終差分、残す互換層、後続で削除する項目と条件を報告する。

## 禁止事項

- リファクタリングを理由に仕様、対象範囲、公開 API を黙って変えない。
- 動かないテストを削除して緑にしない。失敗原因を調べ、テストが不要なら根拠を示してユーザー確認を得る。
- 「将来のため」の抽象化を追加しない。現時点の重複・複雑さを根拠にする。
- 大規模モードでも、承認済みの設計書にないモジュール再編・API 変更・データ移行を進めない。

- [ ] 変更を SAFE / CAREFUL / RISKY に分類した
- [ ] RISKY な変更と仕様変更はユーザー確認済み
