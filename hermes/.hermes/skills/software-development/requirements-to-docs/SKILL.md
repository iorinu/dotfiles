# 要件定義から仕様書を作る

ユーザーとの対話で目的・制約・受入条件を確定し、実装とレビューの基準になる仕様書をプロジェクト内に作成する。未確定の事項を推測で仕様化しない。

## When to Use

- 新機能、変更、問題解決の要件を固めたいとき
- 実装前に受入条件と非機能要件を文書化したいとき
- 実装・レビュー・リファクタリングの共通基準を作りたいとき

使わない場面:
- 既に受入条件まで十分に記載された仕様書があり、実装だけを依頼されたとき
- 文言のみの軽微な修正で、仕様判断を伴わないとき

## 手順

1. 既存文書とコードを調べる。
   - `read_file` と `search_files` で README、既存仕様、関連コード、テスト、プロジェクト規約を確認する。
   - 分かった事実と推測を分ける。

2. 要求を構造化して確認する。
   - 次の項目で不足または曖昧な点があれば、実装前に質問する。
     - 解決したい問題、対象ユーザー、利用場面
     - 対象範囲と対象外
     - 正常系、失敗時、境界条件
     - データ、互換性、性能、セキュリティ、運用上の制約
     - 成功とみなす受入条件
   - 選択肢を示せる場合は `clarify` を使う。実装方針、公開 API、データ形式、外部副作用に影響する不明点は必ず確認する。

3. 仕様書の配置先を決める。
   - プロジェクトに既存の仕様書ディレクトリや命名規則があれば従う。
   - なければ `docs/specs/<feature-slug>.md` を提案する。新規作成前に、既存文書を重複させないことを確認する。

4. 次の見出しを含む仕様書を作成する。
   - 概要と背景
   - 目的、対象外、制約
   - ユーザーストーリーまたは利用シナリオ
   - 機能要件（`FR-001` のような一意 ID を付ける）
   - 非機能要件（必要な場合。`NFR-001` のような一意 ID を付ける）
   - 入出力、状態遷移、エラー処理、互換性（該当する場合）
   - 受入条件（各 ID を参照し、観測可能・テスト可能に書く）
   - 実装上の未決事項と意思決定記録
   - 要件トレーサビリティ表（要件 ID、受入条件、想定テスト）

5. ユーザーに仕様の確定を求める。
   - 仕様書の要約、保存先、未決事項を示す。
   - 「確定」または修正指示を受けるまで、仕様変更を伴う実装には進まない。

## 品質基準

- 「速い」「使いやすい」など測定不能な表現は、数値・条件・観測方法に置き換える。
- 受入条件は実装詳細ではなく外部から確認できる振る舞いで記述する。
- 要件 ID は削除・統合時を除き変更しない。後続のテスト・レビューとの対応を維持する。
- 仕様書には秘密情報、トークン、個人情報を記載しない。

## 完了確認

- [ ] 要求・対象外・制約に未確認の推測がない
- [ ] 機能要件と受入条件に一意 ID がある
- [ ] 正常系、失敗時、境界条件が記載されている
- [ ] 仕様変更に影響する未決事項はユーザーに確認済み
- [ ] 保存先と次に実装する範囲をユーザーが確認済み
