# ループエンジニアリング・スキルの利用ガイド

## 目的

このガイドは、要件を対話で固めて仕様書にし、実装・要件適合レビュー・リファクタリング・再レビューまでを一連の工程として進める 4 つの個人用スキルの使い方を説明します。

スキル一覧:

1. `requirements-to-docs`
2. `spec-driven-delivery`
3. `behavior-preserving-refactoring`
4. `loop-engineering`

スキルは `$HERMES_HOME/skills/software-development/` に保存されます。このガイドは `$HERMES_HOME/docs/loop-engineering-guide.md` にあります。通常の既定値では `$HERMES_HOME` は `~/.hermes` です。

## 使い分け

### 1. `requirements-to-docs`

要件が未確定のときに使います。エージェントは既存コードと文書を確認した後、実装方針・公開 API・データ形式・外部副作用・対象範囲に影響する曖昧さを質問します。

依頼例:

```text
requirements-to-docs を使って、ユーザーが CSV をアップロードして集計できる機能の仕様を作って。
```

仕様書には、機能要件 ID（例: `FR-001`）、受入条件、対象外、エラー処理、非機能要件、テストとの対応表が含まれます。仕様変更が必要なら、実装へ進む前に確認を求めます。

### 2. `spec-driven-delivery`

確定済みの仕様書からコードを作り、要件を満たしているかを確認したいときに使います。

依頼例:

```text
spec-driven-delivery を使って docs/specs/csv-summary.md を実装して。要件適合表も出して。
```

このスキルは、要件 ID ごとに実装箇所とテストを対応付けます。確定済み仕様と依頼範囲内のコード修正は自動で適用します。ただし仕様、公開 API、永続データ形式、外部副作用、対象範囲を変える必要があれば、先に確認します。

### 3. `behavior-preserving-refactoring`

仕様と外部から見える振る舞いを変えずに、実装を読みやすく保守しやすくしたいときに使います。

依頼例:

```text
behavior-preserving-refactoring を使って、今回の CSV 集計機能をリファクタリングして。要件適合は維持して。
```

既定は局所モードです。SAFE（未使用 import の除去など）と CAREFUL（局所的な関数抽出、内部名の変更など）の改善は、テストを実行しながら自動適用します。公開 API、データ形式、並行性、性能特性などに影響する RISKY な変更は、適用前に確認します。

大規模リファクタリングも選べます。モジュール分割、レイヤー再編、依存方向の整理、重複した基盤の統合、段階的な API 移行が対象です。開始前に、対象範囲、維持する外部契約、移行段階、各段階の検証、ロールバック方法を提示して承認を求めます。実行は一段階ずつ行い、各段階のテスト・lint・型検査・ビルドが通るまで次へ進みません。

依頼例:

```text
behavior-preserving-refactoring を大規模モードで使って、src/legacy を新しいモジュール構成へ段階的に移行して。公開 API は維持し、実装前に移行設計書を確認させて。
```

### 4. `loop-engineering`

初めての機能を、要件定義から最終検証まで連続して進めるときに使います。通常はこのスキルを選べば足ります。

依頼例:

```text
loop-engineering を使って、CSV アップロード・集計機能を要件定義から実装、リファクタリング、最終確認まで進めて。
```

実行順:

1. `requirements-to-docs` で仕様書を作成し、仕様を確定する。
2. `spec-driven-delivery` で実装と要件適合レビューを行う。
3. `behavior-preserving-refactoring` で保守性をレビュー・改善する。
4. もう一度 `spec-driven-delivery` の観点で、要件適合と回帰がないことを確認する。
5. 問題があれば実装工程へ戻り、修正して再検証する。

大規模モードを使う場合は、手順 3 を「移行設計書の承認 → 安全網となるテストの追加 → 段階的移行 → 段階ごとの検証」に置き換えます。ループ全体の最終要件適合確認は省略しません。

同じ種類の修正・再検証は既定で最大 3 回です。3 回後も解決しなければ、試行内容と選択肢を示して判断を求めます。

## 期待する入力

依頼には、分かる範囲で次を含めると早く進められます。

- 解決したい問題と対象ユーザー
- 成功と判断する条件
- 既存仕様書や関連ファイルのパス
- 制約（対応 OS、性能、期限、互換性、追加してよい依存関係）
- 対象外にしたいこと

未確定でも構いません。不明点は、スキルが質問して仕様書に記録します。

## 確認が必要になる変更

次の場合は、コードを自動変更せず確認します。

- 仕様や受入条件の変更
- 公開 API、CLI、設定キー、データ形式の変更
- データベースやファイルの破壊的変更
- メール送信、公開投稿、デプロイ、課金などの外部副作用
- 依頼範囲を越える改修
- RISKY に分類されるリファクタリング
- 大規模リファクタリングの対象範囲、移行方式、互換性・ロールバック方針

確定済み仕様と依頼範囲内の実装上の不具合、テスト失敗、要件不適合は自動で修正し、再検証します。

## 完了時に確認するもの

`loop-engineering` は、以下を完了報告に含めます。

- 仕様書のパス
- 実装した要件 ID と変更箇所
- リファクタリングした内容
- 要件適合表の結論
- 実行したテスト、lint、型検査、ビルドの結果
- 未解決事項またはユーザー確認待ち事項

テストやビルドが環境要因・既存不具合で実行できない場合、成功とは扱いません。未検証の範囲とブロッカーを明記します。

## 実用例

最短の依頼は次の形です。

```text
loop-engineering を使って、<作りたい機能> を完成させて。
```

仕様書をすでに持っている場合は、次の形です。

```text
spec-driven-delivery を使って、<仕様書のパス> を実装して。完了後に behavior-preserving-refactoring を実行し、再度要件適合を確認して。
```

小さな修正をすでに実装済みで、設計だけ見直したい場合は、次の形です。

```text
behavior-preserving-refactoring を使って、現在の差分をレビューして改善して。外部の振る舞いは変えないで。
```
